# Сессия 04 — workflow создания автотеста

## Начало сессии

**Цель:** на основе фактической реализации `TC-CALC-001` спроектировать и записать в `WORKFLOW.md` полноценный повторяемый процесс создания одного UI-автотеста, предварительно уточнив у пользователя нераскрытые области.

**Исходный запрос пользователя дословно:**

> Давай создадим воркфлоу по данному флоу созданию автотеста, который был сейчас 
> Задавай вопросы по тем областям которые тебе еще не раскрыты и они нужны для полноценной работы

**Краткий план:**

1. Изучить пустой `WORKFLOW.md` и фактический flow из сессии автоматизации `TC-CALC-001`.
2. По одному уточнить у пользователя аудиторию, границы, правила реализации, диагностики и фиксации прогонов.
3. Предложить короткий дизайн документа и получить явное подтверждение.
4. Записать утверждённый workflow, обновить `REPORT.md` и журнал сессии.
5. Проверить документ на полноту, однозначность и соответствие проектным правилам.

**Используемые агенты:** только основной агент; субагенты не запускаются, поскольку пользователь их не запрашивал.

## Ход работы

- Применены навыки `superpowers:using-superpowers` и `superpowers:brainstorming` для последовательного уточнения требований и согласования структуры до записи документа.
- Задача классифицирована как ограниченная документационная: фактический flow существует в реализации и журнале сессии 03, целевой `WORKFLOW.md` существует, но пока пуст.
- Подтверждено, что `WORKFLOW.md` имеет размер 0 байт; изучены журнал реализации `TC-CALC-001`, текущий `REPORT.md`, Git-история и незакоммиченные изменения предыдущей сессии, которые необходимо сохранить.
- Пользователь определил основного исполнителя workflow: только AI-агент. Документ будет содержать прямые обязательные инструкции, запреты, контрольные точки и критерии завершения для агента.
- Пользователь разрешил обе формы scope одной итерации: один тест-кейс или явно перечисленный пакет кейсов. Агент должен реализовывать только названный scope и не добавлять другие кейсы самостоятельно.
- Пользователь выбрал обязательное согласование: перед реализацией агент всегда показывает короткий дизайн тестов и ждёт явного подтверждения, даже если кейсы выглядят типовыми.
- Для пакетного scope пользователь допускает два варианта структуры: отдельный Java-файл на test case или файл на функциональную область. Конкретный вариант выбирается и согласуется на этапе дизайна с учётом тестового стенда домашней работы и текущего предпочтения пользователя.
- Пользователь запретил вынос тестовой инфраструктуры в отдельные `BaseTest`, page object или helper-классы: локаторы, методы и тесты всегда остаются внутри выбранных `*Test.java` файлов. Это учебное ограничение применяется и при нескольких файлах.
- Пользователь выбрал самодостаточный запуск приложения: каждый тестовый класс проверяет порт 8765, при необходимости запускает `python3 -m http.server 8765` и останавливает только созданный им процесс. Весь suite должен запускаться одной командой `mvn test` без отдельной подготовки сервера.
- Основной браузерный прогон закреплён за системным Chrome в headless-режиме. Headed-режим допускается только как временный диагностический шаг и не должен требоваться для штатного `mvn test`.
- Критерий выбора локаторов сформулирован как принцип, а не жёсткая иерархия: локаторы должны быть стабильными, читаемыми для автотестировщика и не зависеть от хрупкой DOM-структуры или декоративной вёрстки. Нетривиальный выбор объясняется в дизайне; изменение приложения ради тестового локатора требует отдельного согласования.
- В `runs/` после каждой итерации сохраняется Markdown-история всех значимых попыток: команда, время, итог, ошибки/предупреждения, выполненное исправление и финальный результат. Screenshot/trace сохраняются при падении только тогда, когда они использовались или нужны для диагностики.
- Пользователь установил жёсткую границу: workflow не изменяет и не исправляет production-приложение. Если корректный автотест выявляет расхождение со `SPEC.md`, агент сохраняет фактический результат, объясняет расхождение и останавливается; цель домашней работы — качественное взаимодействие с AI, тестовое покрытие и рабочий процесс автоматизации.
- Субагенты используются только по явному запросу пользователя; по умолчанию весь workflow выполняет один основной AI-агент. Если субагенты запрошены, их точные prompts, роли, результаты и принятые решения фиксируются по `AGENTS.md`.
- Согласован нейминг: отдельный файл на кейс — `TcCalc001Test.java`, файл на функциональную область — например `CalculationTest.java`; каждый тестовый файл оканчивается на `Test.java`; методы используют читаемый английский `camelCase`, а `@DisplayName` содержит русский заголовок и ID тест-кейса.
- Уточнено базовое структурное правило: по умолчанию один test case оформляется отдельным `Tc…Test.java`. Группировка нескольких тестов в файл функциональной области применяется только после явного выбора пользователя на этапе согласования конкретного дизайна; детальная логика этой ветки сейчас не проектируется.
- Пользователь исключил обязательный baseline-прогон `mvn test` до реализации. Штатный прогон выполняется после создания или изменения автотестов; предварительный запуск без изменений в workflow не включается.
- Пользователь полностью проанализировал предложенный дизайн `WORKFLOW.md` и явно поддержал формат.
- На основе утверждённого дизайна заполнен `WORKFLOW.md`: зафиксированы источники требований, scope, обязательное согласование, структура самодостаточных Java-тестов, правила локаторов, lifecycle сервера/Chrome, реальный прогон, диагностика, история `runs/`, завершение и Definition of Done.
- Обновлён `REPORT.md` с согласованными решениями и созданным артефактом.
