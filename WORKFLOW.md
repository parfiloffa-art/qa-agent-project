# Workflow создания UI-автотестов

## Назначение

Этот документ задаёт обязательный повторяемый процесс для AI-агента, который
автоматизирует согласованные UI-тест-кейсы кредитного калькулятора на Java,
Playwright и JUnit 5.

Workflow рассчитан на учебный проект. Его цель — получить понятное тестовое
покрытие, воспроизводимый запуск одной командой и прозрачную историю взаимодействия
с AI. Он не предназначен для исправления тестируемого приложения.

## Неподвижные правила

- `SPEC.md` — единственный источник ожидаемого поведения приложения.
- `TEST_PLAN.md` определяет scope, стратегию и приоритеты тестирования.
- `TEST_CASES.md` содержит сценарии, шаги и ожидаемые результаты для автоматизации.
- `AGENTS.md` определяет обязательное журналирование и проектные ограничения.
- Агент полностью читает эти четыре файла перед каждой новой реализацией.
- При конфликте тест-кейса со `SPEC.md` агент ориентируется на `SPEC.md`, сообщает
  о конфликте пользователю и не придумывает новое ожидаемое поведение.
- Агент автоматизирует только явно названный пользователем test case или явно
  перечисленный пакет кейсов. Самостоятельно расширять scope запрещено.
- Агент не изменяет HTML, CSS, JavaScript и другой production-код приложения.
- Если корректный тест обнаружил расхождение приложения со `SPEC.md`, агент
  фиксирует фактический результат и останавливается. Исправлять приложение в рамках
  этого workflow запрещено.
- По умолчанию работает один основной AI-агент. Субагенты используются только по
  явному запросу пользователя и журналируются по правилам `AGENTS.md`.
- Пользователь должен иметь возможность запустить весь suite одной командой:
  `mvn test`.

## Результат одной итерации

Завершённая итерация должна дать:

1. Java-автотесты только для согласованного scope.
2. Реальный полный прогон `mvn test` после реализации.
3. Исправленные ошибки тестового кода и конфигурации автоматизации либо
   зафиксированное расхождение приложения со `SPEC.md`.
4. Историю значимых попыток и фактический финальный результат в `runs/`.
5. Обновлённые журнал сессии и `REPORT.md`.

## Этап 1. Начало сессии

В начале нового чата агент создаёт один новый файл в `sessions/` по формату из
`AGENTS.md`. Один чат использует один файл сессии независимо от количества сообщений.

Сразу записать:

- цель;
- исходный запрос пользователя дословно;
- краткий план;
- используемых агентов;
- явно заданный scope автоматизации.

Не сохранять секреты, персональные данные и внутреннюю цепочку рассуждений.

## Этап 2. Изучение контекста

До предложения реализации агент обязан:

1. Полностью прочитать `AGENTS.md`, `SPEC.md`, `TEST_PLAN.md` и `TEST_CASES.md`.
2. Найти все запрошенные ID в `TEST_CASES.md`.
3. Сопоставить предусловия, шаги и ожидаемые результаты со `SPEC.md`.
4. Проверить `pom.xml`, структуру `src/test`, существующие тесты и соглашения
   проекта.
5. Изучить релевантные HTML-элементы и JavaScript-рендеринг, чтобы выбрать
   стабильные локаторы и понимать момент появления результата.
6. Проверить `git status` и сохранить все существующие пользовательские изменения.

Если требование отсутствует или допускает существенно разные реализации, агент не
угадывает — он задаёт пользователю один уточняющий вопрос за раз.

Baseline-прогон `mvn test` до изменения кода не выполняется.

## Этап 3. Обязательное согласование дизайна

Перед написанием или изменением Java-кода агент всегда показывает короткий дизайн,
даже если сценарий кажется простым.

Дизайн должен назвать:

- точный scope и ID кейсов;
- создаваемые или изменяемые файлы;
- выбранную структуру файлов;
- основные локаторы и принцип их стабильности;
- lifecycle браузера и локального HTTP-сервера;
- методы взаимодействия со страницей;
- проверяемые результаты;
- команду финального прогона и способ фиксации истории.

После показа дизайна агент останавливается и ждёт явного подтверждения пользователя.
Начинать реализацию до подтверждения запрещено.

## Этап 4. Структура Java-тестов

### Вариант по умолчанию

Один test case оформляется в отдельном файле. Имя строится из ID без дефисов в
Java-стиле и обязательно заканчивается на `Test.java`:

```text
TC-CALC-001 -> TcCalc001Test.java
```

Для явно запрошенного пакета по умолчанию создаётся отдельный файл на каждый case.

### Группировка по функциональной области

Несколько тестов можно объединить в один файл функциональной области, например
`CalculationTest.java`, только если пользователь явно выбрал этот вариант при
согласовании дизайна конкретной итерации. Без такого выбора агент использует вариант
«один case — один файл».

### Содержимое файла

Для этой домашней работы каждый `*Test.java` самодостаточен. Локаторы, lifecycle,
методы и тесты находятся в одном файле и разделены читаемыми блоками, например:

1. конфигурация и локаторы;
2. подготовка и завершение;
3. методы взаимодействия и вспомогательные проверки;
4. тесты.

Запрещено создавать отдельные `BaseTest`, page object и helper-классы. Допустимое
дублирование между тестовыми файлами считается учебным ограничением проекта.

Методы тестов называются читаемым английским `camelCase`. `@DisplayName` содержит
ID и русское название исходного test case.

## Этап 5. Требования к реализации

### Локаторы

Локатор должен быть одновременно:

- стабильным при нерелевантных изменениях вёрстки;
- понятным автотестировщику без расшифровки;
- однозначным в пределах страницы или конкретного блока.

Можно использовать стабильные `id`, `name`, доступные роли и labels, а также узкие
CSS-локаторы внутри понятного контейнера. Выбор зависит от фактического DOM.

Не использовать без необходимости:

- позиционные `nth-child` и индексы;
- длинные CSS-цепочки;
- абсолютный или длинный XPath;
- декоративные классы;
- текст, который не является частью проверяемого контракта.

Нетривиальный выбор локатора объясняется в дизайне. Если стабильного локатора нет,
агент запрашивает согласование и не добавляет `data-testid` или другие изменения в
production-код самостоятельно.

### Действия и проверки

- Тест взаимодействует с реальной страницей через Playwright, без моков приложения.
- Методы скрывают повторяющиеся пользовательские действия, но не прячут смысл
  сценария.
- Проверки соответствуют наблюдаемому результату из `SPEC.md` и `TEST_CASES.md`.
- Ожидаемые значения задаются независимыми литералами. Нельзя вычислять expected
  теми же формулами или функциями, которые использует приложение.
- Тест не проверяет внутреннюю реализацию JavaScript, если case описывает поведение
  пользователя.
- Асинхронные состояния ожидаются средствами Playwright или проверкой условия, а не
  произвольными длинными паузами.

### Локальный сервер

Каждый тестовый класс должен обеспечивать запуск приложения как часть `mvn test`:

1. Проверить доступность `http://127.0.0.1:8765`.
2. Если приложение недоступно, запустить из корня проекта
   `python3 -m http.server 8765 --bind 127.0.0.1`.
3. Дождаться фактического HTTP-ответа с ограниченным timeout.
4. Запомнить, был ли процесс создан этим классом.
5. После тестов остановить только процесс, созданный этим классом.

Нельзя завершать уже работавший пользовательский сервер.

### Браузер

- Штатный прогон использует системный Chrome через Playwright.
- По умолчанию Chrome запускается в headless-режиме.
- Headed-режим разрешён только как временный диагностический шаг.
- Browser, context/page и Playwright закрываются в lifecycle-методах даже после
  падения теста.
- Штатный успешный прогон не должен требовать ручного открытия браузера или сервера.

## Этап 6. Реальный прогон

После реализации агент запускает из корня проекта точную команду:

```bash
mvn test
```

Финальный вывод должен явно содержать количество выполненных тестов, failures,
errors, skipped и итог Maven-сборки.

Во время диагностики разрешён узкий запуск выбранного класса или метода, но он не
заменяет финальный полный `mvn test`.

## Этап 7. Диагностика

При падении или неожиданном предупреждении агент:

1. Полностью читает сообщение, stack trace и Surefire-артефакты.
2. Проверяет, воспроизводится ли проблема.
3. Устанавливает причину до внесения исправления.
4. Определяет категорию проблемы:
   - тестовый код;
   - конфигурация автоматизации или окружения;
   - расхождение приложения со `SPEC.md`.
5. Вносит минимальное исправление только в тестовый код или конфигурацию
   автоматизации.
6. Повторяет релевантный прогон, затем полный `mvn test`.

Если причина находится в production-приложении:

- не изменять приложение;
- не ослаблять корректную проверку ради зелёного результата;
- сохранить фактическое падение и доказательства;
- объяснить расхождение пользователю;
- остановить итерацию без самостоятельного bug fix.

Неудачные попытки и отрицательные результаты нельзя скрывать.

## Этап 8. История прогонов

После каждой итерации создать или обновить Markdown-файл в `runs/`. Рекомендуемое
имя:

```text
YYYY-MM-DD-<scope>.md
```

Файл должен содержать:

- дату и время;
- точную команду;
- тестовые классы или scope;
- окружение: Java, JUnit, Playwright, браузер и URL;
- число tests, failures, errors и skipped;
- итог Maven-сборки и длительность;
- все значимые попытки по порядку;
- текст ошибки или предупреждения в безопасном объёме;
- установленную причину;
- выполненное исправление;
- фактический финальный результат.

Screenshot и Playwright trace сохраняются только при падении и только если они
использовались или нужны для диагностики. В истории дать путь к сохранённому
артефакту и кратко объяснить его назначение.

Не сохранять в истории секреты и чувствительные данные.

## Этап 9. Завершение

Перед финальным ответом агент:

1. Проверяет, что автоматизированы только согласованные ID.
2. Проверяет, что все тестовые файлы заканчиваются на `Test.java`.
3. Проверяет отсутствие отдельных base/page object/helper-классов.
4. Проверяет читаемость и устойчивость локаторов.
5. Проверяет, что production-код и требования не изменены.
6. Проверяет актуальный Surefire-результат полного `mvn test`.
7. Проверяет `git diff --check` и просматривает итоговый diff.
8. Обновляет `REPORT.md` после значимого этапа.
9. Дополняет файл сессии разделами из `AGENTS.md`: что сделано, что не сделано,
   что не получилось, следующий шаг и статус.

Финальный ответ пользователю должен кратко назвать созданные тесты и артефакты,
привести фактический результат `mvn test` и явно сообщить, если итерация остановлена
из-за расхождения приложения со `SPEC.md`.

## Definition of Done

Итерация завершена, если выполняются все применимые условия:

- [ ] Scope явно задан и не расширен.
- [ ] Требования и тест-кейсы полностью изучены.
- [ ] Дизайн показан пользователю и явно подтверждён.
- [ ] Структура файлов соответствует согласованному варианту.
- [ ] Локаторы, методы и тесты находятся внутри выбранных `*Test.java`.
- [ ] Production-приложение не изменено.
- [ ] `mvn test` действительно запущен после реализации.
- [ ] Ошибки автоматизации исправлены и проверены повторным прогоном.
- [ ] Расхождение приложения, если оно найдено, зафиксировано без product fix.
- [ ] Все значимые попытки и финальный результат сохранены в `runs/`.
- [ ] `REPORT.md` и журнал сессии обновлены.
- [ ] Пользователь получил фактический итог, а не только описание созданного кода.
